# Saved-Clash release repair v2 — source review

Recorded 2026-10-02. **Source-only review; no database connection or SQL execution.** The release bundle contains a deliberately revised saved-row repair. The eight migration blocks remain identical to their canonical sources. The inherited `supabase/repairs/2026-09-24-saved-clash-fields.sql` and `scripts/foundation/savedClashRepair.mjs` were preserved; regenerating from that older generator would discard this reviewed bundle revision.

The inherited roster update could rewrite an unchanged JSON value on every rerun when a full-box line existed but its name or position was unavailable. Its audit also counted every preview candidate null as recoverable, even without a recoverable candidate snapshot, and did not count missing positions. Those findings justify the bundle divergence.

The v2 repair uses the same recovery plan in the before audit, updates, private audit log and after audit. Every public update has an `IS DISTINCT FROM` guard. Candidate and roster updates also require that the current value matches the value captured by the plan; coach updates require the current field to remain SQL-null. The plan preserves existing non-null values, roster IDs, order and other JSON keys. It fills a name only from a nonblank string in the matching stored full-box line, and a position only from PG/SG/SF/PF/C. Malformed roster shapes, unknown coaches and unavailable snapshot fields remain untouched. Existing preview candidate fields must agree with a complete snapshot tuple before a partially populated tuple is completed. An entirely empty tuple may recover whatever valid fields its recorded candidate supplies. Production-engine null identity and neutral coaches remain valid.

The private v2 backup is `ops_backup.saved_clashes_20261002_v2`. `CREATE TABLE IF NOT EXISTS` preserves its first snapshot on reruns; this does not refresh a backup after later games arrive. The inherited dated backup remains separate. The private repair log records each repair observation, including a rerun that changes no saved rows. There are no public repair inserts or deletes.

After execution on the correct project, `saved_total` must remain unchanged and `repairable_saved_rows` plus every exact `*_recoverable` count should reach zero, unless concurrent new recoverable rows arrived. Raw `*_missing`, candidate metadata remaining after the plan, invalid-shape and mismatch counts may remain. They require review; zero raw missing is not a safe repair requirement. Record actual update counts from the SQL Editor. A rerun should update zero saved rows, while recording one new private log observation. These are source-derived expectations, not observed results.

The machine-readable [source review](../../data/validation/loop-foundation/release-sql-source-review-2026-10-02.json) records source hashes and these checks:

- Eight ordered migration blocks match the canonical files after trimming surrounding whitespace.
- All 329 statements and all 39 SQL/PLpgSQL function bodies pass pglast 8.4 syntax parsing using PostgreSQL 18.4 grammar. The target server version and runtime type/schema resolution were not observed.
- All 21 public tables enable RLS: 20 user-data tables plus `schema_migrations`.
- All 25 policy creates have a matching `DROP POLICY IF EXISTS`; all five career/activity views use `security_invoker=true`.
- All 21 SECURITY DEFINER function definitions set a fixed search path and revoke client execution from PUBLIC, anon and authenticated.
- All five public repair updates have actual-change and original-value/null guards. All five copies of the recovery-plan CTE are identical.

The expected RLS shape is specific, not simply “21 rows true.” Authenticated profile/history, saved-roster, preference, progression, competitive and private public-profile-table reads are scoped by owner. Saved-roster writes and preference writes remain owner-scoped. Saved-Clash browser writes remain limited to favorites, guarded against authoritative-field changes. Challenge creators may read their challenges and responses; an authenticated participant may read its own attempts. Rivalry members may read their rivalry, periods and events. The `schema_migrations`, challenge-secret, rivalry-block and rivalry-request-log tables deliberately have no client policy. Raw competitive/public-profile tables do not become publicly readable; server projection functions provide filtered public views.
