# Public profile contract V1 (Phase 9F)

> A public profile answers **WHO IS THIS ERACLASH PLAYER?** It never answers
> what personal information we hold about the account.

An EraClash account is **private by default**. Creating one does not create a
publicly discoverable profile, and appearing on the Phase 9E leaderboard grants
nobody access to anything else. Public exposure is explicit, minimal,
reversible, safe and decided by the server.

`PUBLIC_PROFILE_POWER_EFFECT = 0` is a contract constant and an invariant the
gates prove: no roll, draft, era, coach, placement, Legend Rival, Challenge,
Competitive Rating or XP path reads any of this. Phase 9F **consumes** rating
and progression state for display and computes nothing competitive.

Version `PUBLIC_PROFILE_VERSION 1.0.0`. The pure contract is
`src/profiles/contract.js`; the server is `api/_lib/profiles.js`, dispatched by
`api/profile.js` (no new serverless function — the budget is full at 13); the
schema is `supabase/migrations/0007_public_competitive_profiles_v1.sql`.

## Two independent switches

| Preference | Governs | Default |
| --- | --- | --- |
| `leaderboard_visibility` (9E) | inclusion in the public Competitive Rating leaderboard | `private` |
| `profile_visibility` (9F) | access to the richer public competitive profile | `private` |

They are **never combined**. All four states are legitimate and each is
preserved exactly as chosen:

| Profile | Leaderboard | Profile reachable | On leaderboard | Row links |
| --- | --- | --- | --- | --- |
| private | private | no | no | no |
| private | public | no | **yes** | no |
| public | private | **yes** | no | no |
| public | public | yes | yes | **yes** |

A player may want a ranking without a clickable profile, or a shareable profile
without being in the global listing. Both are supported on purpose.

`profile_visibility` joins the closed 9B.2 vocabulary: every previously
approved key stays valid, unknown keys stay rejected, and it accepts only
`private` or `public`. Nothing about preference validation was weakened.

## The safe public identifier

An opaque slug generated by the database: **20 symbols of a 32-symbol
alphabet — 100 bits**. Crockford's base32 without `i`, `l`, `o` and `u`, so a
slug read aloud or retyped is unambiguous. `extensions.gen_random_bytes(20)`
with `byte % 32`; 256 is divisible by 32, so there is no modulo bias.

- stable across display-name changes and every profile edit
- not derived from an email, not the auth id, not a row id
- not sequentially enumerable
- minted **with the account**, so nothing has to be created at the moment a
  profile goes public — and it means nothing while the profile is private
- immutable: `PUBLIC_PROFILE_SLUG_IMMUTABLE`, because a shared link must keep
  resolving and a chosen slug would leak identity
- gone with the account

Route: `/player/<slug>`.

## What a public profile may carry

`slug`, `displayName`, `initials`, `state`, `level`, `featured`, `placement`,
`profileVersion` — and, **only once placed**, `rating`, `rank`, `wins`,
`losses`, `ties`, `matches`, `winPct`.

A field is absent unless the contract lists it, and no field is added merely
because the database holds it. `FORBIDDEN_PROFILE_FIELDS` names what must never
appear: email, auth or database ids, provider, phone, location, join date, IP,
session, cookies, tokens, saved rosters, favorites, the XP ledger, private
achievements, challenge or attempt ids, seeds, preferences and deleted-name
history.

The data comes from `profile_public_get(slug)` — a `SECURITY DEFINER` function
with a **fixed select list**. There is no base row for a client to filter, so no
field can leak by being forgotten in a component.

## Provisional stays private

Phase 9E kept a provisional rating private until placement:
`competitive_leaderboard` requires placement, and `competitive_rank_of` returns
nothing for a provisional account. Phase 9F preserves that **publicly**.

A public profile that has not placed shows:

```
COMPETITIVE
PROVISIONAL
3 / 5 RATED MATCHES
2 / 3 UNIQUE OPPONENTS
```

No rating. No rank. No estimate, and nothing that computes "would be #X". The
two placement counts *are* public — they are the whole provisional card.

The account **owner** still sees their own provisional rating, exactly as Phase
9E already showed them.

A rank appears only when the account is placed **and** its leaderboard
visibility is public. `publicProfile()` deliberately does not re-derive that
rule: `leaderboard_visibility` is a private preference that must never travel
in a public payload, so a public row simply carries the rank it was granted, or
none. The database is the authority.

## Featured achievements

Up to **three** already-unlocked achievements, in the order chosen. The server
reads unlock state from the account's own `achievement_unlocks` and
`profile_set_featured()` refuses anything locked, unknown, duplicated,
malformed or beyond three — **as a whole**, so a rejected list is never
partially applied. Clearing is allowed and idempotent.

Phase 9D is untouched: no achievement definition, unlock rule or XP value
changed, and 9F created no achievement of its own.

## No enumeration

There is **no listing endpoint of any kind**. `profile_public_get` takes one
slug and returns at most one row. A private profile, an unknown slug, a
malformed slug, an auth uuid supplied as a slug, an empty string and a deleted
account all return **the same thing**: no rows, `found: false`. Nothing reveals
whether an account exists.

The one function that takes no identifier, `profile_board_links(limit)`,
returns rank→slug pairs for accounts **already displayed on the public Top
100** that opted in *twice*. It is bounded by Phase 9E's own
`competitive_rank_of`, cannot return anything the leaderboard does not already
show, and exists so a row can link to a profile that chose to be linkable. The
Phase 9E leaderboard remains the one intentionally bounded public competitive
listing.

## Sharing, and the Open Graph limitation

Sharing is the Web Share API where the browser offers it, the clipboard
otherwise, and the raw link last. No social SDK. No tracking parameter. Nothing
about the viewer in the URL, and no auth or session data in a shared link.

**Dynamic Open Graph metadata is not implemented in V1, and this is a
documented limitation rather than an omission.** The deployment's serverless
function budget is full at 13 (12 API routes plus the preview-access
middleware — both `api/share-page.js` and `middleware.js` record this), so a
per-profile Open Graph renderer has no slot of its own. `api/share-page.js`
could serve one under `?kind=player`, but every human visit would then take a
redirect hop into the app, and the Player Card would have to exist twice — once
as server HTML and once as the React component — which is exactly the fragile
side system worth avoiding. `/player/<slug>` is therefore an ordinary SPA
route, like `/leaderboard` and `/my-eraclash`, and a crawler preview shows the
site-level card.

The requirement V1 does meet is the one that matters: **the profile itself is
worth sharing.** No image-generation infrastructure was added.
