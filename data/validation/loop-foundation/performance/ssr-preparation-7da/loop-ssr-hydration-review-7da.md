## Verdict

Whole-App prerendering plus `hydrateRoot` is possible as a future architecture change, but is not a safe drop-in performance change for the existing home, Modes hub and Daily routes. It requires an explicit identical first-render contract for route, viewport layout, local remembered state, identity and server clock/config. The installed React 18.3.1 exposes `renderToString` and `hydrateRoot`; Vite 5.4.x exposes SSR loading/build primitives, but this repository has no App SSR server/client entries or hydration wiring. New React 19 static-prerender APIs must not be assumed available.

React requires matching initial server/client content; mismatches are bugs and attributes are not guaranteed to be corrected. `renderToString` does not wait for suspended lazy components or effect-fetched data. See [React hydration](https://react.dev/reference/react-dom/client/hydrateRoot), [React string rendering](https://react.dev/reference/react-dom/server/renderToString), and [Vite SSR integration](https://vite.dev/guide/ssr.html). Current official React documentation describes a newer React version; this review relies only on APIs also present in the installed React 18 runtime.

## Bounded alternatives considered

1. **Selected by parent:** stable eager LoopModes discovery, with its inner screens still lazy; the reviewed 14 conditional component boundaries; lightweight theme application; exact-native compressed PNG delivery. This removes the initial lazy LoopModes request without changing API, draft, callback or day semantics. Residual LCP failures remain open. No additional configuration loader or hydration change is selected here.
2. **Source-only, not selected:** overlap the existing `loopApi({op:'config'})` with a required mode import from the parent route entry. Reuse exactly one promise through an explicit single-use handoff. Existing `loopApi` only deduplicates while pending and deletes the entry on completion; using that alone would duplicate config when prefetch finishes before mount. Any handoff must scope to current account generation/API instance/day, invalidate on auth changes and New York reset/focus, preserve authoritative response dates/errors/retry, and never serialize bearer tokens or owner hints. A rejected preload must remain recoverable with the existing visible Retry. It must not run on home or Modes hub, must not call daily-start/roll/play, must not change guest cookies/claims/quotas, and must not replace official config with locally calculated data. This would only target the measured Daily request chain; no acceptance evidence was generated.
3. **Source-only, not selected:** route-specific modulepreload hints derived from emitted hashed LoopModes script/CSS names, not hard-coded filenames or every-route unconditional preload. Vite already preloads dependencies when the dynamic import runs; an earlier HTML hint changes discovery, not route semantics. Current same-index fallback would require safe route-specific serving or a small CSP-compliant external discovery module. The compiled LoopModes module imports the entry chunk, so evaluation is not independent of entry initialization. Regressions in homepage bandwidth, update caching or missing assets must be checked; no gain is assumed. See [Vite preload generation](https://vite.dev/guide/features.html#preload-directives-generation).

No static shell duplication, fake server clock/config, fixture rendering, premature draft reservation, alternate simulation data, hidden Lighthouse-only markup or threshold waiver is proposed.
